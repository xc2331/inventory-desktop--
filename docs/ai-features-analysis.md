# AI 四功能开发分析

> 对应设置页「AI 能力说明」中的四项能力：拍照分割物品、图像识别建议、票据批量录入、条码 / NFC 扫描。
> 本文用于评估实现路径、工作量与风险，为后续排期提供依据。

---

## 1. 拍照分割物品

### 用户价值
- 拍摄一张桌面/储物箱照片，自动把多个物品切分成独立图片，分别填入物品照片。
- 减少逐件拍照、逐件建卡片的重复劳动。

### 技术方案
| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A. 云端视觉 API（如 OpenAI GPT-4o / Claude 3.5 / 阿里云视觉智能） | 上传图片，返回每个物品的边界框 + 裁剪图 | 准确率高、无需本地算力 | 图片上传涉及隐私；有调用成本；需要联网 |
| B. 本地传统 CV（OpenCV 轮廓检测 + GrabCut） | 在 Electron 主进程或 Node 调用 opencv4nodejs | 完全离线、无费用 | 背景复杂时效果差；引入原生依赖会增加打包体积 |
| C. 本地轻量模型（Transformers.js + Segment Anything 小模型） | 浏览器/Node 端运行 ONNX 模型 | 离线、隐私安全 | 对电脑 GPU/内存要求高；首次加载慢；准确率不如云端 |

### 推荐实现
- **MVP**：方案 A，通过设置页配置 API Key，调用支持 vision 的多模态大模型。
- 模型返回边界框后，前端用 Canvas 裁剪并压缩为 Base64，回填到物品照片字段。
- 后续再评估是否引入本地模型作为离线 fallback。

### 关键接口
- 输入：`image: base64` + 提示词 "请识别图中独立物品，返回每个物品的 bounding box (x1,y1,x2,y2) 和名称建议"。
- 输出：`[{ box: [x1,y1,x2,y2], name: string }]`。

### 工作量与风险
- 工作量：中（约 3-5 天）。
- 风险：模型返回格式不稳定；需要多次提示工程；大模型可能遗漏小物品。

## 2. 图像识别建议

### 用户价值
- 用户上传单张物品照片，AI 自动给出物品名称、分类、存放位置、数量等建议。
- 在新建/编辑物品时作为「智能填充」按钮。

### 技术方案
- 同样优先使用云端多模态大模型（GPT-4o / Claude / 国产视觉模型）。
- 通过系统提示词固定输出 JSON Schema：
  ```json
  {
    "name": "建议名称",
    "category": "对应分类 key",
    "quantity": 1,
    "confidence": 0.9
  }
  ```
- 识别结果仅作「建议」，用户确认后才写入表单。

### 与现有数据结合
- 将现有分类列表拼进提示词，让模型返回已存在的 `category` key。
- 若置信度低，标记为黄色提示，让用户手动选择。

### 工作量与风险
- 工作量：小（约 2-3 天）。
- 风险：分类命中依赖提示词质量；英文/中文分类名需要匹配当前语言。

## 3. 票据批量录入

### 用户价值
- 拍照发票、小票、购物清单，AI 提取商品名称、数量、金额、购买日期，批量生成物品记录。
- 适合采购后一次性入库。

### 技术方案
- 云端 OCR + LLM 两步：
  1. OCR 识别票据文字（如百度/腾讯/阿里通用票据识别，或 GPT-4o 直接读图）。
  2. 将 OCR 文本交给 LLM，按指定 JSON 数组输出。
- 输出示例：
  ```json
  [
    { "name": "生抽", "quantity": 2, "amount": 15.8, "date": "2026-07-30" }
  ]
  ```

### 交互流程
1. 在物品列表新增「票据入库」按钮，进入批量录入页。
2. 支持拖拽/粘贴/手机传图上传多张票据图片。
3. 前端展示 AI 识别结果表格，允许人工增删改。
4. 点击「确认入库」，批量调用 `createItem`。

### 工作量与风险
- 工作量：中偏大（约 5-7 天）。
- 风险：票据格式差异大；金额/数量识别容易出错；需要较多人工校对 UI。

## 4. 条码 / NFC 扫描

### 用户价值
- 扫描商品条码自动填充名称、规格；扫描 NFC 标签快速定位物品。
- 提升入库和盘点效率。

### 技术方案

#### 条码扫描
- **手机端**：复用现有的二维码局域网传图服务，扩展一个 `/barcode` 页面，调用手机摄像头 + `ZXing` 或 `barcode-detector` API 识别条码，把条码文本回传电脑。
- **电脑端**：Electron 调用摄像头（`navigator.mediaDevices.getUserMedia`）+ `ZXing` JS 库实时识别。
- 拿到条码后，调用公开商品库（如 Open Food Facts 等免费 API）查询商品信息；若查不到，提示用户手动填写。

#### NFC 扫描
- NFC 依赖硬件，Electron 桌面端一般没有 NFC 模块。
- 可行做法：通过手机 NFC 读取标签 ID，通过局域网回传；或在物品详情页让用户手动输入 NFC ID 用于后续检索。

### 推荐实现
- **MVP**：优先做手机扫码条码（复用 QR 上传通道），电脑端条码扫描可作为补充。
- NFC 作为「标签绑定」字段先落地：在物品表单增加 `nfc_id` 字段，支持手动录入或手机回传。

### 工作量与风险
- 工作量：条码扫描约 3-4 天；NFC 完整流程约 4-6 天。
- 风险：商品条码库中文商品覆盖不全；NFC 需要用户有支持 NFC 的手机。

## 统一设计建议

1. **配置集中化**：在设置页增加「AI 服务」面板，统一配置 API Key、模型选择、是否启用视觉识别。
2. **隐私默认本地**：除条码查询外，所有图像识别优先走用户自己配置的 Key，数据不经过我们服务器。
3. **结果可撤销**：AI 识别结果均作为「建议」，必须用户确认后才写入数据库。
4. **错误兜底**：模型失败或网络异常时，给出明确提示并保留用户手动输入入口。
5. **渐进上线**：建议按「图像识别建议 → 拍照分割物品 → 票据批量录入 → 条码/NFC 扫描」的顺序发布，降低一次性改动面。

## 下一步需要确认

1. 是否允许上传图片到云端大模型？如果不行，则优先投入本地模型方案。
2. 是否已有倾向的 AI 供应商（OpenAI / 阿里云 / 百度 / 本地部署）？
3. 条码扫描的商品信息来源希望用哪个？是否需要支持离线条码库？
4. NFC 功能是否必须手机回传，还是先在桌面端提供手动绑定字段即可？
